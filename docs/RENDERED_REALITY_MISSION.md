## How ORACLE Serves RenderedReality

The full pipeline from signal to continuity:

```
Approved Signals
    ↓
Event Structuring
    (raw activity → clean event objects with type, source, project, timestamp)
    ↓
Live Context State
    (related events grouped into operational context — what is happening now)
    ↓
Candidate Meaning
    (ORACLE renders interpretation — what does this context mean?)
    (status: PENDING_HUMAN_APPROVAL — not yet stored)
    ↓
Memory Retrieval
    (cross-reference candidate meaning against existing memory)
    (have we seen this project? what did Noah decide? what rules apply?)
    ↓
SOV1 Approval
    (SOV1 / Noah reviews candidate meaning — approve, reject, or correct)
    (51/49 Human Sovereignty Rule: ORACLE renders 49%, Noah approves 51%)
    ↓
Durable Memory
    (approved meaning written to oracle_memory.db)
    (facts, decisions, projects, people, milestones, open loops)
    ↓
Recommended Action
    (ORACLE retrieves memory and surfaces useful next steps)
    (draft, remind, suggest, flag, warn, propose)
    ↓
RenderedReality Continuity
    (nothing important is lost — Noah can ask what he worked on, what he decided,
     what matters, what is open, what he promised, what he built)
```

The formula:
```
Raw Activity + Current Context + Retrieved Memory = Meaningful Action
```

## Passive Observation Design (Planned)

ORACLE should be able to observe approved signals passively — without Noah actively interacting.

**Approved passive sources:**
- File changes in approved folders (repo, Projects/, approved OneDrive paths)
- App context (window title, active application name — not content)
- Calendar events (upcoming commitments — not raw email body)
- Clipboard (only on explicit capture request, not continuous)
- Browser tab titles (not full page content)
- Time spent in applications (activity heatmap — no keystrokes)

**Never passive-observed:**
- Raw keystrokes (outside ORACLE's own input fields)
- Passwords, form fields, banking portals
- Camera or microphone feeds (always OFF unless Noah explicitly enables)
- Other people's systems or files
- Full email body (subject line and sender only, pending approval)

**Observation architecture (planned — not yet implemented):**

```
core/observer.py       — file system watcher, window title poller, event emitter
core/event_buffer.py   — volatile event queue, cleared on privacy mode
core/meaning_engine.py — LLM compression of event buffer into candidate meaning
core/integration_gate.py — ApprovalGate (already implemented)
```

First safe implementation: file system watcher on approved folders only.
No keystrokes. No camera. No mic. No auto-ingest.

## LootDrop and RenderedReality

Mythic LootDrops are how RenderedReality marks breakthrough moments.

When ORACLE ships something that changes how Noah operates — a new vision system, a sovereignty gate, a mission-critical module — it is not just a commit. It is a moment that should be remembered.

Mythic LootDrop metadata:
```json
{
  "tier": "MYTHIC",
  "source_activity": "what triggered this",
  "reason_earned": "why this tier was awarded",
  "related_project": "which project or system",
  "timestamp": "ISO datetime",
  "significance": "what this moment means for RenderedReality",
  "suggested_follow_up_action": "what to do next"
}
```

Mythic drops are stored in `lootdrop_mythic` memory category.
They are always surfaced first in recap summaries.
They are the compressed record of the moments that mattered most.
